# Configurable Multi-Position ROI Measurements Design

**Date:** 2026-07-11

**Target branch:** `codex/first-run-hardware-setup`

**Feature branch:** `codex/configurable-multi-position-roi`

**Planned PR title:** `feat(operator): support configurable multi-position ROI measurements`

## 1. Goal

Extend the YY/T 1771 G3 workstation from one ROI to one through six configurable measurement positions while preserving the existing single-ROI API and artifact contracts. One camera frame and one temperature reading are shared by every enabled position; detection state, outlier filtering, formal curves, AFAS analysis, status, and exports remain independent per position.

This change does not alter camera connection logic, temperature-controller connection logic, detector mathematics, or AFAS mathematics. Operator mode continues to force `detector_mode=contrast_widest_span` and exposes only the existing contrast threshold and maximum-jump controls in addition to the position editor.

## 2. Chosen Architecture

Use an additive, dual-layer compatibility structure.

- New code uses `regions`, `region_results`, `region_detection_results`, and `analysis.regions`.
- Legacy `roi`, top-level `detection_result`, `curve_points`, `live_point_status`, `detection_results`, and top-level analysis fields continue to represent the first enabled position, normally `region_1`.
- Old payloads that contain only `roi` or top-level analysis fields are normalized to one enabled `region_1` during validation or import.
- New manifests and exports always include the multi-position representation even when only one position is configured.

This duplicates the first position in compatibility fields, but avoids silently changing the meaning of existing lists whose length currently equals the number of captured frames.

## 3. Domain Model

### 3.1 Constants

The shared position limits and default palette are:

```text
MIN_MEASUREMENT_REGIONS = 1
MAX_MEASUREMENT_REGIONS = 6

REGION_COLORS = [
  "#ef4444",
  "#3b82f6",
  "#22c55e",
  "#f59e0b",
  "#a855f7",
  "#06b6d4",
]
```

Backend validation owns the 1–6 invariant. The frontend mirrors the constants for immediate UI feedback.

### 3.2 MeasurementRegion

```python
class MeasurementRegion(G3Model):
    region_id: str
    index: int
    label: str
    enabled: bool = True
    roi: RotatedROI
    color: str
```

Rules:

- `region_id` is non-empty and unique within one measurement definition.
- `index` is positive and unique in saved definitions; the frontend renumbers visible order after add/remove without changing IDs.
- `label` defaults to the localized position name generated by the frontend; backend migration uses `位置 1` for the default legacy wrapper.
- `color` must be a CSS hex color in `#RRGGBB` form.
- A region retains its ID and color when other regions are deleted.
- A newly added region takes the first palette color not currently used and a non-conflicting `region_N` ID. Existing IDs are never rewritten merely because display order changes.

### 3.3 MeasurementDefinition compatibility

`MeasurementDefinition` becomes:

```python
roi: RotatedROI | None = None
regions: list[MeasurementRegion] = []
```

A pre-validation normalization applies these rules:

1. `roi` present and `regions` absent creates the default enabled `region_1` using that ROI and the first palette color.
2. `regions` present uses the region list as authoritative.
3. After normalization, `roi` is synchronized to the first enabled region by ascending `index`; in normal UI-created data this is `region_1`.
4. Total regions must be between one and six.
5. At least one region must be enabled.
6. Every region must contain a valid `RotatedROI`; therefore every enabled region is directly measurable.
7. Region IDs and indices must be unique.

The frontend prevents disabling the last enabled position and prevents deleting the last total position. The backend rejects any invalid payload even if it bypasses the UI.

### 3.4 DetectionResult metadata

`DetectionResult` gains defaulted compatibility metadata:

```python
region_id: str = "region_1"
region_index: int = 1
region_label: str = "位置 1"
region_color: str = "#ef4444"
```

Detector algorithms still operate on a temporary single-region `MeasurementDefinition` whose `roi` is the selected region ROI. A service helper attaches region metadata to the returned result. No detector formula changes are required.

### 3.5 RunManifest dual representation

`RunManifest` contains:

```python
detection_results: list[DetectionResult]
region_detection_results: list[DetectionResult]
```

- `detection_results` remains one result per frame for the first enabled region.
- `region_detection_results` is the long-form list of all enabled frame-region results.
- A legacy manifest without `region_detection_results` is normalized by copying its `detection_results`, whose default metadata maps it to `region_1`.
- One `FrameRecord`, one `TemperatureRecord`, and at most one preview image are stored per captured frame, regardless of region count.

## 4. Per-Frame Detection Pipeline

Introduce a focused multi-region service boundary that accepts one source frame, one normalized measurement definition, one synchronized temperature reading, and per-region state maps. It returns ordered results for all enabled regions.

```text
capture frame once
read/synchronize temperature once
prepare shared frame representation once where supported
for each enabled region ordered by index:
    derive a single-region measurement using region.roi
    detect on that ROI
    apply region-local temporal/candidate state
    attach the same frame timestamp and temperature reading
    apply the region-local outlier filter
    create curve points and live point status
return all region results
```

The state maps are keyed by stable `region_id`:

- `candidate_states_by_region`
- `detector_policy_states_by_region`
- `temporal_stabilizers_by_region`
- `outlier_filters_by_region`
- `temperature_distance_points_by_region`

No region reads a baseline, pending state, or previous candidate from another region. A normal invalid detection for one region remains a result for that region and does not interrupt the others. An unexpected region-local detector exception is converted to an `INVALID` result with a traceable exclusion reason; the exception is recorded for diagnostics without terminating the frame event.

The existing detector is allowed to crop and preprocess each ROI independently. Shared conversion of the full source frame to grayscale may be cached once per frame where the detector entry point supports it without changing detector behavior. Source acquisition, temperature acquisition, and preview encoding are never repeated per region.

## 5. Probe and Live Event Contracts

### 5.1 RegionResult payload

Both probe responses and live frame events use:

```json
{
  "region_id": "region_1",
  "region_index": 1,
  "region_label": "位置 1",
  "color": "#ef4444",
  "detection_result": {},
  "curve_points": {},
  "live_point_status": {}
}
```

`live_point_status` includes `region_id`, current formal temperature-distance point count, presence/missing reason, detection status, curve-point status, temperature-sync status, and outlier-filter status.

### 5.2 Probe

One call to “Probe current frame” captures or loads one frame, reads/synchronizes temperature once where applicable, and returns:

- one `image_data_url`;
- `region_results` for all enabled positions;
- a combined overlay description;
- legacy top-level `detection_result` and `overlay` for the first enabled position.

### 5.3 Live run

At run start, the normalized `measurement_definition`, including the ordered regions and their ROIs, is snapshotted into the run manifest. The frontend disables add, delete, enable/disable, rename, and ROI editing until the run completes or stops.

Each `frame` event includes all `region_results`. Top-level compatibility fields mirror the first enabled result. A position that lacks a formal point does not prevent other position points from being emitted and appended during the same event.

After stop, analysis emits progress in region order:

```text
analyzing_region current=1 total=3 region_id=region_1
analysis_region_complete region_id=region_1
analyzing_region current=2 total=3 region_id=region_2
analysis_region_complete region_id=region_2
...
complete
```

The frontend displays `正在分析位置 {current}/{total}` / `Analyzing position {current}/{total}`. A failed region produces a failed `RegionAnalysisResult` and does not prevent later regions from completing.

## 6. Analysis Model

Add:

```python
class RegionAnalysisResult(G3Model):
    region_id: str
    region_index: int
    region_label: str
    color: str
    all_frames: list[DetectionResult]
    distance_time: list[CurvePoint]
    raw_distance_time: list[CurvePoint]
    stabilized_distance_time: list[CurvePoint]
    temperature_time: list[CurvePoint]
    temperature_distance: list[CurvePoint]
    raw_temperature_distance: list[CurvePoint]
    stabilized_temperature_distance: list[CurvePoint]
    afas_preprocessing: dict[str, Any]
    afas_analysis: dict[str, Any]
    summary: dict[str, Any]
```

`AnalysisResult.regions` contains one result for every enabled run-snapshot region. Existing top-level curve and AFAS fields mirror the first enabled result. Legacy analysis data without `regions` is wrapped as `region_1` during import/model validation.

AFAS preprocessing and analysis are invoked independently for each region with the unchanged global parameter set. The summary exposes raw and smoothed point counts, AS, AF, delta T, maximum-slope temperature, status, and failure reason. Insufficient points or an AFAS exception affects only that region.

Re-analysis applies the submitted global AFAS parameters to every region and returns the same dual representation.

## 7. Operator UI

### 7.1 Position preset panel

The Operator left panel receives a `Measurement positions` section before the collapsed numeric ROI editor. It displays an array-driven list, never six hard-coded fields.

Each position row contains:

- color swatch and localized label;
- enabled/disabled control;
- active-edit selector / `Edit ROI` action;
- current distance;
- current detection or exclusion status;
- formal point count and latest formal-point frame;
- delete action.

Behavior:

- A new measurement starts with one enabled position.
- Add is disabled at six and shows the maximum-position message.
- Delete is disabled at one total position.
- Disabling the last enabled position is prevented with the at-least-one message.
- All structural and ROI controls are disabled during a run.
- Rename support is implemented in state and data models; the initial Operator UI may use an inline label input so the exported label remains user-visible and stable.

Pure state helpers live outside the page component:

```text
normalizeMeasurementRegions()
addRegion()
removeRegion(regionId)
updateRegionRoi(regionId, roi)
setActiveRegion(regionId)
toggleRegionEnabled(regionId)
renameRegion(regionId, label)
```

### 7.2 Multi-region frame overlay

The frame canvas accepts the normalized region list, active region ID, and results keyed by region ID.

- Every enabled ROI is rendered using its region color.
- Every available A/B segment and points use the same color.
- Only the active region receives pointer handlers and resize/rotate handles.
- The active region has a stronger outline and label.
- Disabled regions may be shown dimmed while editing but do not show formal A/B overlays.
- Engineering mode retains the existing single-ROI props and behavior through a compatibility adapter.

### 7.3 Live state and combined trend

Live state is stored as:

```typescript
regionResultsById: Record<string, RegionLiveState>
regionCurvesById: Record<string, CurvePoint[]>
```

Each region immediately appends its formal point from the frame event. Display smoothing remains a frontend-only moving-window transformation performed independently per visible region. It does not modify `AnalysisResult`, AFAS inputs, manifest data, or exports.

The combined temperature-distance chart computes one shared x/y domain across visible regions and draws up to six colored series. Legend controls toggle visibility without mutating data. Tooltip content identifies position label, temperature, distance, frame index, detection status, and temperature-sync status. Optional point downsampling is deterministic and display-only.

### 7.4 Results and history

The result page shows one summary card/row per region and one combined temperature-distance/AFAS chart. Each legend entry controls that region’s raw formal points, live/display trend, and AFAS-smoothed curve layers. A failed region remains visible with its failure reason while successful regions retain their results.

History import uses `analysis.regions` when present. Old imports are normalized to one position and use the same multi-region components.

## 8. Export and Import

The ZIP preserves legacy artifacts and adds:

```text
frame_results.csv                         legacy region_1 CSV
temperature_distance.png                  legacy region_1 chart
roi_ab_overlay.png                        legacy region_1 overlay
frame_results_long.csv                    all enabled frame-region rows
frame_results_wide.csv                    one row per frame, region columns
regions/<safe_region_id>_frame_results.csv
analysis_by_region.json
run_export.json
parameters.json
temperature_distance_combined.png
temperature_distance_<safe_region_id>.png
roi_ab_overlay_combined.png
```

Long CSV uses one row per frame-region and includes stable region metadata before the existing detection, temperature, synchronization, and outlier fields. Wide CSV uses one row per frame and predictable columns derived from region IDs. Per-region CSVs keep the existing core field order after their region identity prefix.

`run_export.json` includes the full normalized measurement definition, both manifest result representations, and `analysis.regions`. `parameters.json` includes global detector and AFAS parameters plus every region ROI and color.

All region IDs are sanitized for artifact filenames, while the unsanitized stable ID remains inside CSV/JSON fields. Disabled positions remain in the saved measurement definition but do not receive official run rows or region analysis/export artifacts.

The importer prefers `frame_results_long.csv` and `analysis.regions` for new exports, accepts the legacy files as fallback, and normalizes old one-position JSON/ZIP data to `region_1`.

## 9. Error Handling and Invariants

- Backend validation returns a structured 422 error for zero total regions, more than six regions, no enabled regions, duplicate IDs/indices, invalid colors, or invalid ROIs.
- Operator controls explain the one-position minimum and six-position maximum before a request is sent.
- Region-local invalid detection and outlier filtering are ordinary per-region statuses.
- Region-local AFAS failure is captured in that region summary.
- Frame acquisition or temperature acquisition failure remains frame/run-level because those resources are shared.
- A failed preview image write does not produce per-region image retries.
- Run snapshot regions are immutable for that run even if the user later edits a new setup.

Implementation follows red-green-refactor cycles.

Backend coverage includes:

- legacy ROI migration and all region validation invariants;
- synthetic three-ROI detection with distinct distances;
- one camera call and one temperature call per multi-position frame;
- independent candidate, temporal, policy, and outlier state;
- per-region formal curve inclusion/exclusion;
- partial AFAS failure isolation;
- long/wide/per-region export contents and legacy artifacts;

Frontend coverage includes:

- probe and frame-event compatibility fallback;
- independent live curve updates and smoothing;
- legend toggles and multi-region hover metadata;
- multi-region result summaries and combined result chart;
